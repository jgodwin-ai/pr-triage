# PR Triage Bot — Design Specification

## Overview

A standalone, Dockerized React application that helps developers efficiently triage large pull requests — especially those generated by AI coding agents. The tool uses Claude to analyze PR diffs, group related changes into logical clusters, rank them by importance, and present a layered view that lets reviewers focus on the 10-20% of changes that actually need human attention.

## Target Users

- **MVP:** Individual developers reviewing PRs on GitHub.com (public and private repos). They supply their own Anthropic API key and GitHub token.
- **Future:** Engineering teams with centralized deployment (GitHub App / CI integration). Architecture should not preclude this path.

## Core Concept: Layered Review

Instead of a flat file diff, the tool presents PR changes at three zoom levels:

1. **Executive Summary** — 2-3 sentences: what the PR does, what needs attention, what's noise.
2. **Change Clusters** — related changes grouped and ranked by reviewer priority. Each cluster is tagged ("needs-review", "low-risk", "boilerplate", "style-only") with a summary explaining *why* it matters or doesn't.
3. **Annotated Diffs** — line-by-line diffs within a cluster, with inline agent notes highlighting specific concerns (security issues, logic bugs, convention violations, etc.).

Users navigate via breadcrumbs: `PR Summary → Cluster → File`. Click to drill in, back to zoom out.

## Architecture

### Project Structure

```
pr-triage-bot/
├── docker-compose.yml          # Orchestrates all services
├── Dockerfile                  # Builds frontend + backend together
├── .env.example                # PORT_PREFIX, ANTHROPIC_API_KEY, GITHUB_TOKEN
├── .gitignore                  # Includes .env, .superpowers/, node_modules, etc.
├── frontend/                   # React + TypeScript (Vite)
│   ├── src/
│   ├── package.json
│   └── vite.config.ts
├── backend/                    # Node.js + TypeScript (Express)
│   ├── src/
│   └── package.json
├── analyzer/                   # Python (FastAPI) — Phase 2+
│   ├── Dockerfile              # Separate Dockerfile (Python base image)
│   └── src/
└── docs/
```

### Services

**Phase 1 — Single container ("app"):**
- Express backend serves the Vite-built React frontend as static files
- In dev mode, Vite dev server runs inside the container with hot reload
- Backend handles: GitHub API calls, Claude agent orchestration, WebSocket streaming

**Phase 2+ — Adds "analyzer" container:**
- Python FastAPI sidecar for deep code analysis
- Backend calls analyzer via internal Docker network HTTP
- Analyzer handles: repo cloning, AST parsing, dependency graphs, convention checking

### Communication

- **Frontend ↔ Backend:** REST for actions + WebSocket for streaming analysis results
- **Backend ↔ Analyzer:** Internal HTTP API (Docker network, not exposed externally)

### Worktree-Friendly Dev

- `docker-compose.yml` uses a `PORT_PREFIX` env var (default `90`)
- Default ports: `9000` (app in dev), `9002` (analyzer)
- Each git worktree sets a different `PORT_PREFIX` in its `.env` (e.g., `91` → `9100/9102`)
- Multiple instances can run simultaneously without port conflicts
- All services have volume mounts for hot reload

## Token / Key Management

Keys are resolved in this order:

1. `.env` file in project root (gitignored) — `ANTHROPIC_API_KEY`, `GITHUB_TOKEN`
2. Environment variables (for Docker/CI)
3. Frontend input as fallback — if backend has no keys, UI shows input fields

The frontend checks `GET /api/config/status` on load to determine whether keys are pre-configured. If they are, key input fields are hidden.

Keys sent via the frontend are held in backend memory for the duration of the analysis only — never persisted to disk.

## Multi-Agent Analysis Pipeline

When a user submits a PR URL, the backend orchestrates three Claude agents in sequence:

### Agent 1: File Analyzer

- **Input:** Individual file diffs (chunked to stay within context limits)
- **Execution:** Runs in parallel across files
- **Output:** Array of `FileAnalysis` objects
- **Job:** Summarize each file's changes, categorize (logic/style/config/boilerplate/test), assign initial impact score (1-5)

### Agent 2: Clustering Agent

- **Input:** All `FileAnalysis` results from Agent 1
- **Output:** Array of `ChangeCluster` objects
- **Job:** Group related changes into logical clusters, name them descriptively, write cluster-level summaries

### Agent 3: Ranking & Synthesis Agent

- **Input:** All `ChangeCluster` objects from Agent 2
- **Output:** Final `PRAnalysis` with executive summary
- **Job:** Rank clusters by reviewer importance, write executive summary, tag clusters (needs-review/low-risk/boilerplate/style-only), generate inline diff annotations for high-priority items

### Streaming UX

Results stream to the frontend via WebSocket as each agent completes:

```
→ { type: "status", stage: "file-analysis", progress: "12/34 files" }
→ { type: "status", stage: "clustering", progress: "grouping changes" }
→ { type: "partial", clusters: [...] }
→ { type: "status", stage: "ranking" }
→ { type: "complete", analysis: PRAnalysis }
```

The user sees the executive summary first, then clusters populate progressively. No waiting for the full pipeline to finish.

## Data Model

```typescript
interface PRAnalysis {
  id: string;
  pr: PRMetadata;
  executiveSummary: string;
  clusters: ChangeCluster[];
  timeSaved: string;
}

interface PRMetadata {
  url: string;
  title: string;
  author: string;
  baseBranch: string;
  headBranch: string;
  additions: number;
  deletions: number;
  fileCount: number;
}

interface ChangeCluster {
  id: string;
  name: string;
  summary: string;
  tag: "needs-review" | "low-risk" | "boilerplate" | "style-only";
  priority: number;
  files: FileAnalysis[];
  insights: string[]; // Phase 2+: ripple effects, conventions, etc.
}

interface FileAnalysis {
  path: string;
  summary: string;
  category: "logic" | "style" | "config" | "test" | "boilerplate" | "docs";
  impactScore: number;
  diff: string;
  annotations: DiffAnnotation[];
}

interface DiffAnnotation {
  lineStart: number;
  lineEnd: number;
  type: "warning" | "info" | "suggestion";
  message: string;
}
```

## Phase Breakdown

### Phase 1: Core MVP (Frontend + Backend + Agent Pipeline)

- Landing page: PR URL input, optional API key inputs (hidden if .env configured)
- GitHub API integration: fetch PR metadata, file list, diffs
- Multi-agent pipeline: File Analyzer → Clustering Agent → Ranking Agent
- Layered UI: executive summary → change clusters → annotated diffs
- WebSocket streaming for progressive result display
- Dockerized: single `docker compose up`, parameterized ports
- Hot reload in dev mode

**Delivers:** A working tool that takes a PR URL and gives you a prioritized, clustered review with inline annotations.

### Phase 2: Deep Code Analysis (Python Analyzer Sidecar)

- Shallow clone of the repo into the analyzer container
- AST parsing via tree-sitter for multi-language support
- Dependency graph construction: what functions/modules does this change touch, what depends on them
- "Ripple effect" analysis: identify callers/dependents that may be affected by changes
- Convention checking: does new code follow existing naming, structure, error handling patterns
- Redundancy detection: did the PR introduce functionality that already exists
- Test coverage assessment: are changed code paths covered by tests
- Results enrich each `ChangeCluster` and `FileAnalysis` with structural insights

**Delivers:** Analysis that goes beyond LLM inference — grounded in actual code structure.

### Phase 3: Semantic Understanding (Knowledge Graph)

- In-memory knowledge graph (NetworkX) built from repo code structure
- Maps relationships: calls, imports, inherits, implements, tests
- Cross-file impact scoring: changes to highly-connected nodes scored as higher risk
- Enhanced agent prompts include graph context for smarter clustering and ranking
- Optional graph visualization showing change impact radius
- Swappable storage backend (can upgrade to embedded DB or Neo4j later)

**Delivers:** Holistic codebase understanding — the analysis knows not just what changed, but how it connects to everything else.

## Non-Goals (for now)

- GitHub Enterprise Server or GitLab/Bitbucket support
- Persistent storage / database (analyses are ephemeral)
- User accounts or multi-tenancy
- GitHub App / webhook integration
- Commenting directly on PRs from the tool
- Support for non-GitHub PR URLs
